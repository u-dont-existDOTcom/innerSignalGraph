# InnerSignal instruction consumer map

## Purpose and authority

This map tells maintainers where instructions originate, which consumer may receive them, and what enforces that boundary. It is maintenance routing, not an always-injected checklist and not therapy, model, installation, or release authority.

Current owner and task requirements remain highest. `AGENTS.md`, `.github/codex-repository.json`, `state/CODEX-CURRENT-STATE.md`, `README.md`, `AUTOPILOT.md`, this index, current code/tests, and relevant live Universal guidance retain their established order. Installed behavior still comes only from `stable`; therapy/framework changes and promotion remain owner-gated.

## Boundary invariants

- Do not paste Universal, Mission Control, repository governance, or reasoning-selection prose into therapy system prompts, private case packets, guide text, graphs, or delivered responses.
- Do not let a developer worker applying a bounded patch acquire application-supervisor, therapy-policy, owner, merge, installation, or release authority.
- Do not infer that similarly named providers share a contract. The application-owned high-effort reviewer and a developer execution session are distinct consumers with distinct inputs and gates.
- Preserve source wording, structured fields, and provider receipts separately. A document describing a method, model, or effort level does not prove that any provider received or executed it.
- Private audit and repair receive only the authorized packet. Repository-aware adapters, producer traces, prior verdicts, tools, filesystem access, and persistent sessions cannot substitute for the required isolation contract.
- Passing replay preservation or canonical candidate assembly is only admission to the existing next gate. It is not semantic approval, owner approval, promotion, installation, or release.
- Protective compatibility and threat urgency remain separate decisions. A child-contact restriction is not proof of imminent danger, and a prompt or model audit is not a clinical-clearance service.

## Maintenance

Update this map when a material change adds a new instruction source or consumer, changes where a source is injected, changes a role's provider/model configuration, or alters an enforcement gate. Keep detailed routing here instead of expanding the root bootstrap. Verify executable claims against current call sites and tests; documentation alone is not mechanical evidence.

## Longitudinal synthesis: known versus new (2026-10-17)

`src/prompts/longitudinal-synthesis.mjs` defines the four longitudinal rules the app roles already followed (salience, the established target, known answers, repeated advice) and the owner's KNOWN VERSUS NEW rules from issue #172 (`AMEND.CROSS.KNOWN_VERSUS_NEW_SYNTHESIS_20261017`): before calling anything in a review across sessions, records or journal material new, check it against the established record and say what it is and what it changes; an imported journal's model-made labels are search aids; a priority keeps its source; safety and consent can override the order. `longitudinalClinicalRules` uses the same lines and adds the audit failure `KNOWN_PRESENTED_AS_NEW` (both scoped to reviews: an ordinary turn about a familiar difficulty stays a listening turn), so they reach case audit, candidate drafting, critique, adjudication, realization, private audit and repair; the extraction records observations and composes no review. MCP hosts get the byte-matched `references/LONGITUDINAL-SYNTHESIS.md`, read before every response. `load_handoff`, `load_case_context` and `load_case_context_by_alias` results also carry `therapy_rules`: that file and `references/PROTOCOL-STATE-PROVENANCE.md`, byte for byte with the protocol's identity, so a host that opens a case has them even if it never loaded the protocol. `tests/longitudinal-synthesis.test.mjs` and `tests/therapy-protocol-mcp.test.mjs` check delivery; they do not demonstrate model adherence.

## Applying the rules: a test with models (2026-10-17)

The delivery tests above show that the rules reach every consumer; they can't show that a model follows them. The owner's answer to question 40 for issue #172 (the chat had loaded protocol 0.2.1 and still set protective action against reparenting) made that the failure to test. `npm run eval:protocol-application` (`src/evals/protocol-application.mjs`, `docs/PROTOCOL-APPLICATION-EVAL.md`) gives a model the served protocol, an opened synthetic case and its journal quotes exactly as a connector process returns them (this checkout's, or an earlier commit's with `--git-ref`), and a model of the other family grades the reply against a fixed rubric written from the owner's definition: protective acts within reparenting, services separate, known not called new, tags not findings, frame consent, urgent safety first, and what the new material changes. The judge is checked first on known replies, including the split the owner saw. It calls models, so it runs by hand; `tests/protocol-application-eval.test.mjs` checks the test itself with fake models.
