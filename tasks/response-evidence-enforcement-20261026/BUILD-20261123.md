# Response evidence enforcement: build contract for slices 2, 3, 4 and 6

Status: **build contract for one implementation branch; it adds no authority beyond the merged design**.

Date: 23 November 2026. Base: `main` at `67443fc1f`. Branch: `claude/response-evidence-enforcement-20261123`.
Authority, in order: the owner's request of 26 October 2026 (issue #195), the merged design
(`docs/superpowers/specs/2026-10-26-response-evidence-enforcement.md`, "the design") and plan
(`docs/superpowers/plans/2026-10-26-response-evidence-enforcement.md`, "the plan"), then this file. Where this file is silent,
the design decides. This file fixes the concrete names, shapes and rules the design left open, so the slices can be built and
reviewed against one contract.

Already merged and not rebuilt here: slice 1 (communication evidence and delivery states, #203) and slice 5 (controlled
supervisor draft review and exact export #210, its connector #211). This branch builds what is left: slice 2 (the trusted
snapshot and bounded retrieval), slice 3 (the source-support review and one shared admission check), slice 4 (fallbacks and
recovery) and slice 6 (the behavioral evaluation and the capability readback).

## 1. Switch and rollout

- One setting, `INNER_SIGNAL_RESPONSE_EVIDENCE`, parsed by `src/core/on-off-setting.mjs` like the other on/off settings
  (anything else stops the start). Default **off**. `loadConfig` reads it into `config.responseEvidenceEnforced` (boolean).
- **Off** means advisory, exactly as today: no snapshot is created, the audit prompt, schema and packet are byte-identical to
  `main`, and every existing test passes unchanged. Turning it on is the owner's release decision.
- **On** means enforced, for the runtime and the supervisor path together:
  - the runtime controller and the supervisor draft service create a snapshot for every new candidate lineage, so every new
    candidate is **governed** (section 2);
  - the store refuses approval, transcript delivery and export of any candidate that is not governed
    (`RESPONSE_EVIDENCE_REQUIRED`). Already-sent history is untouched; a pending ungoverned candidate must be superseded and
    re-run (design section 11: no silent migration, no retroactive approval).
- A governed candidate is always fully checked at every exit, whatever the setting says later. There is no flag that waives it.
- The store takes the policy as an option, `responseEvidencePolicy: "advisory" | "enforced"` (default `"advisory"`). The access
  service passes it from its own option, and every place that builds the access service from configuration passes
  `config.responseEvidenceEnforced ? "enforced" : "advisory"`.
- Content-free readback (design slice 6 "Release boundary"): `/health` and the private connector's ready line gain
  `responseEvidence: { runtime: "advisory" | "internal_runtime_enforced", supervisorExport: "advisory" |
  "supervisor_export_enforced", journalProvider: "unconfigured" | "configured" }`. Never a case id, text, digest or setting value.

## 2. Governed candidates and the snapshot

### Where snapshots live

A new additive field of the encrypted case record, `response_evidence_snapshots: []`, within record version 7, added by
`normalizePrivateCaseRecord` when absent (exactly like `communication_events` and `supervisor_artifacts`), validated by
`validatePrivateCaseRecord`, append-only and immutable in `assertAppendOnly`. Limits: at most 20,000 snapshots per case; one
serialized snapshot at most 96,000 UTF-8 bytes. Older code keeps the unknown field through its own writes (check it as PR 203 did).

### ResponseEvidenceSnapshotV1

Built only by trusted store code inside one `mutate` (store method `freezeResponseEvidence`), from the record's own projections
plus a journal part supplied by server code (the controller's provider; never a model, never a caller field it cannot vouch for).
A replay with the same `snapshotId` and the same inputs returns the stored snapshot; different inputs under the same id are refused.

```text
{
  schema_version: 1, id, policy_version: "response-evidence-v1", case_id, created_at,
  owner: { kind: "runtime_turn", runtime_turn_id } | { kind: "supervisor_draft", operation_key },
  revision: 1 | 2 | 3, parent_snapshot_id: null | id,
  revision_reason: "initial" | "dependency_refresh" | "evidence_expansion",
  candidate_origin: "backend_produced" | "external_draft",
  original_writer_source_inclusion: "verified" | "not_attested",
  inbound: { turn_id, exact_text_sha256, audience: "client", source_kind: "exact_client_turn" },
  dependency_binding: {
    transcript_digest,            // effective transcript with amendments applied, EXCLUDING the inbound turn (section 3)
    amendments_digest,
    communication_digest,         // active communication events, excluding this lineage's own exposed/exported bookkeeping
    established_context_digest,   // canonical digest of record.case_state at freeze time
    supervisor_inputs_digest,     // ids of owner-supplied supervisor inputs
    compatibility_state_binding,  // as compatibilityStateBinding() returns it
    journal_bindings: [ { corpus_id, generation, visibility_epoch } ]
  },
  source_items: [ {
    id,                // "src:turn:<turn id>", "src:report:<event id>", "src:draft:<candidate id>:v<version>", "src:input:<entry id>", "src:journal:<n>"
    kind,              // see the kinds table below
    actor,             // "client" | "assistant" | "supervisor" | "owner" | "unknown"
    audience,          // "client" | "supervisor" | "private_journal" | "unknown"
    time: { at: string | null, status: "known" | "unavailable" },
    epistemic_status,  // "exact_client_words" | "app_committed_text" | "owner_reported" | "agent_relayed_report" | "client_written_account" | "unsent_draft" | "unknown_delivery"
    excerpt_sha256, excerpt_bytes,
    exact_excerpt,     // required for journal and for draft/report text not in the transcript; null for transcript turns (resolved by locator)
    locator            // { kind: "transcript_turn", turn_id } | { kind: "candidate", candidate_id, candidate_version } | { kind: "supervisor_input", entry_id } | { kind: "journal", corpus_id, generation, visibility_epoch, record_id, start_byte, end_byte }
  } ],
  communication_projection: { confirmed_or_reported_client_outbound, supervisor_only_artifacts, unresolved_delivery, omitted },
  history_requirements: [ { id, topic, why_material, source_ids, disposition: "answered_by_sources" | "retrieval_requested" | "unavailable" | "open" } ],
  journal: {
    availability: "not_configured" | "not_authorized" | "unavailable" | "available",
    retrieval_status: "not_attempted" | "returned" | "no_match" | "partial" | "failed" | "budget_exhausted",
    receipts: [ { operation_id, corpus_id, generation, visibility_epoch, purpose: "session_use", query_sha256, filters_sha256,
                  returned_source_ids, packet_sha256, more_available, omitted_count, budget_used_tokens, budget_used_bytes } ],
    coverage: string | null, more_available: boolean, omissions: [ { reason, count } ],
    budget: { max_tokens: 8000, max_bytes: 64000, used_tokens, used_bytes }
  },
  snapshot_sha256    // sha256 of the canonical JSON of every other field (sorted keys, the project's existing canonical form)
}
```

Source item kinds and what each can support:

| Kind | From | Can support |
| --- | --- | --- |
| `exact_client_turn` | a user turn of the effective transcript | personal history, history-dependent advice, conflicts, claims about what the client said; that the client saw a text the client quotes (only the quoted words) |
| `app_committed_client_outbound` | an assistant turn the communication projection marks `app_committed` | prior delivery of exactly that text |
| `owner_reported_client_outbound` | an active `reported_sent` event resolved to exact bytes, `owner_action` origin | prior delivery (reported provenance) |
| `agent_relayed_report` | an active `reported_sent` event with `agent_relayed` origin, or any unresolved report | nothing by itself: prior delivery only when worded as reported/uncertain |
| `unsent_draft` | a draft, exposed or exported candidate with no delivery or report | that the text was NOT delivered; never support for prior delivery |
| `unattributed_assistant_turn` | an assistant turn the projection cannot attribute | nothing about delivery (audience unknown) |
| `relayed_client_message` | a supervisor input of type `client_message` | what the owner relayed, with its `supplied_by` |
| `supervisor_instruction` | a supervisor input of type `supervisor_revision` | the supervisor's instruction only; never client history |
| `journal_quotation` | an authorized session-use journal excerpt | the client's written account (not independent verification of the events it describes) |
| `journal_retrieval_record` | the snapshot's journal part itself (availability, retrieval status, coverage, omissions), present whenever a journal part exists, `not_configured` included | claims about which sources were or were not consulted and what a search did or did not return; never personal history |

Amended 23 Nov 2026 after the first live evaluation run (development evidence): `exact_client_turn`, `app_committed_client_outbound`, `owner_reported_client_outbound` and `relayed_client_message` also support `source_consultation_claims` (a reply may truthfully say what it rests on, such as "you told me"), and the `journal_retrieval_record` kind was added, because a no-match or unavailable search left nothing citable for a true statement about the search.

Which transcript turns become items: the last 40 effective transcript turns plus every turn referenced by
`case_state` item sources, at most 200 items in all, oldest omitted first with an explicit omission entry. Transcript items store
no text (their locator and `excerpt_sha256` bind the effective text); the model-facing view (section 4) resolves the text from the
record and refuses to build if a digest no longer matches.

The model's case state and the writer's proposed state updates are **never** source items (design section 5: a candidate's own
proposed formulation cannot corroborate itself).

### The binding on a governed candidate

A reserved candidate metadata key, `response_evidence`, written only by trusted store paths and refused from callers (like
`supervisor_draft`, through `rejectReservedCandidateMetadata`):

```text
{ schema_version: 1, policy_version: "response-evidence-v1", snapshot_id, snapshot_sha256,
  candidate_origin, writer_inclusion: "verified" | "not_attested", writer_inclusion_sha256: string | null,
  established_context_after_commit_sha256: string | null, dependency_status: "current_at_commit" | "stale_at_commit" }
```

- Runtime original candidate: `commitPrivateRuntimeCandidate` takes `responseEvidence: { snapshotId, writerInclusionSha256 }`. Inside
  the same mutation the store checks the snapshot exists, belongs to this runtime turn, and that the sealed `candidate`
  invocation's completed output carries the same snapshot sha and inclusion sha. It recomputes the dependency binding of the
  record **before** applying the writer's state: equal to the snapshot's binding → `current_at_commit` and, after applying the
  state, `established_context_after_commit_sha256` = digest of the new `case_state`; otherwise `stale_at_commit` and null. The
  candidate is stored either way (stale work is preserved, never deliverable: design section 8).
- Runtime repair: binds the snapshot the repair writer received (the turn's newest revision), with the repair invocation's
  inclusion receipt; `established_context_after_commit_sha256` is inherited from the lineage root.
- Supervisor draft: bound in `submitSupervisorDraft` / `reconstructSupervisorDraft`; the established context digest is the
  snapshot's own (a submission changes no case state). External drafts are `writer_inclusion: "not_attested"`.

## 3. Dependency binding and what invalidates

`computeEvidenceDependencyBinding(record, { inboundTurnId, lineageRootId })` is deterministic code over the record:

- the inbound turn is excluded from `transcript_digest` by id and bound separately by its id and exact-text sha, so the runtime's
  first candidate commit (which moves the inbound from `runtime_turns[].inbound` into the transcript) changes nothing;
- the lineage's own exposed/exported/reported bookkeeping is excluded from `communication_digest` (reuse the supervisor module's
  `foreignCommunicationSignature` rule rather than writing a second one);
- audit bookkeeping, receipts and timestamps are not inputs, so writing an audit never invalidates its own input.

Invalidating (each must be shown by a test): a newer client turn; any transcript amendment; a delivery correction or any new
foreign communication event; a new owner input; a changed protective-compatibility binding; a changed journal generation,
visibility epoch or tombstone for a bound corpus; any change of `case_state` after the lineage's own commit (an owner plan decision,
an operator state save). Not invalidating: the lineage's own commit, its audits, its approval, its own export events.

## 4. What the models receive

- **Writer** (backend-produced): `durableCaseContextBlock` renders `context.response_evidence` when present, after the journal
  block, as one block headed `VERIFIED DELIVERY AND SOURCE EVIDENCE`. The model runtime returns
  `responseEvidenceInclusion: { snapshot_id, snapshot_sha256, view_sha256 }`, where `view_sha256` is the digest of the exact view
  object rendered. A test captures the actual provider requests and finds the exact block in the request that writes the final text.
- **Auditor**: the sealed audit packet gains `response_evidence` (the model-facing view: snapshot id and sha, origin and writer
  inclusion, inbound, every source item with its exact text resolved, the communication projection, history requirements, journal
  availability and coverage, and fixed review instructions) and the disclosure manifest gains
  `response_evidence_snapshot_sha256` and `response_evidence_view_sha256`. Without a snapshot the packet, prompt and output schema
  are byte-identical to `main`.
- **Repair**: the repair packet carries the same view and the failed audit's findings, including the derived evidence findings
  (section 5), and the repair prompt adds the narrow repairs the design names (introduce a suggestion as new; qualify uncertain
  history; use a known prior answer; ask without presupposing). Its inclusion receipt is returned like the writer's.

## 5. The source-support review (EvidenceReviewV1)

The auditor's JSON gains `evidence_review` (required when the packet carries `response_evidence`):

```text
evidence_review: {
  coverage: [ { dimension, status: "assessed" | "no_applicable_items", reason } ]   // all five, each once
  items: [ { id, dimension, kind: "claim" | "recommendation" | "question_presupposition",
             candidate_quote, quote_occurrence, source_ids, assessment, reason } ],
  missing_material_history: [ { id, question, why_material, candidate_quote, quote_occurrence } ]
}
dimensions: prior_delivery | personal_history | history_dependent_advice | source_consultation_claims | coverage_scope_and_conflicts
assessment: supported | contradicted | unsupported | uncertain_but_worded_accurately
```

Mechanical rules (code, in `src/supervisor/response-evidence-contract.mjs`; semantics stay with the auditor):

1. The model quotes; the server locates. `candidate_quote` must occur exactly in the candidate's UTF-8 bytes (no whitespace or
   Unicode normalization); `quote_occurrence` (1-based, default 1) picks the occurrence. The server stores
   `candidate_span { start_utf8_byte, end_utf8_byte, span_sha256 }`. An unlocatable quote, a missing dimension, a duplicate id,
   an unknown source id or a bad field makes the review **malformed**: a validation error inside the model runtime's validate
   step, so the invocation fails and is retried within the existing attempt limit (design: malformed output is an operational
   failure, not a clinical verdict).
2. `supported` and `contradicted` need at least one source id. A `supported` item whose sources cannot support its dimension
   under the kinds table (for example an `unsent_draft` cited for prior delivery, or a `supervisor_instruction` cited for personal
   history) is **downgraded by code** to a blocking `RESPONSE_EVIDENCE_SOURCE_INCOMPATIBLE` finding.
3. Derived blocking findings, computed by code from the review alone, with severity `substantive`, id `evidence:<item id>`:
   `RESPONSE_EVIDENCE_UNSUPPORTED` (each `unsupported` item), `RESPONSE_EVIDENCE_CONTRADICTED` (each `contradicted` item),
   `RESPONSE_EVIDENCE_SOURCE_INCOMPATIBLE` (rule 2) and `RESPONSE_EVIDENCE_MISSING_HISTORY` (each `missing_material_history`
   entry). The model's own ordinary findings are kept beside them unchanged. No "minor" label can remove a derived finding.
4. The stored audit evidence gains `response_evidence: { schema_version: 1, policy_version, snapshot_id, snapshot_sha256,
   auditor_inclusion_sha256, review (normalized, with spans), derived_finding_ids }`, and its `audit_version` is
   `private-candidate-audit-v5`. Ungoverned audits keep v4 and their exact shape.
5. The store recomputes rules 1-3 from the stored review and refuses evidence whose findings do not contain exactly the derived
   ones, so a caller cannot submit an unsupported item with an empty findings list.

History-dependent advice, as the auditor is told (design sections 6 and 9; amended 23 Nov 2026 after the first live run showed the
earlier wording blocking suggestions offered as new when history was simply unknown, which the design's availability table permits
as current-message support): advice depends on history when whether the method was tried before, what happened, or a barrier to it
would change the advice. When the sources settle that, the advice is checked against them: advice that repeats what the sources say
failed, or ignores a barrier they state, is contradicted, even with no historical claim in its wording. When the sources do not
settle it, a suggestion that says or implies nothing about the person's past with the method is current-message support, assessed
`uncertain_but_worded_accurately`; `missing_material_history` is for a response that itself asserts, presupposes or depends on an
answer the sources do not give.

## 6. The shared admission check

`assessResponseEvidenceAdmission(record, candidate, { policy, point })` in `src/supervisor/response-evidence-contract.mjs`
returns `{ admissible, code, reasons }` with fixed reason words only. For a governed candidate it requires all of: the bound
snapshot exists, belongs to this case and lineage, and its sha recomputes; the candidate origin and writer inclusion match the
snapshot (a backend writer's inclusion receipt present, an external draft `not_attested`); the approving audit carries a valid
`response_evidence` for this exact candidate id, version, sha and snapshot, with the auditor inclusion receipt matching the sealed
audit invocation (runtime) or the supervisor review receipt (supervisor path); no derived blocking finding; and the current
dependency binding equals the snapshot's, with `established_context_after_commit_sha256` equal to the digest of the current
`case_state`. For an ungoverned candidate it admits under `advisory` and refuses under `enforced`.

Codes: `RESPONSE_EVIDENCE_REQUIRED`, `RESPONSE_EVIDENCE_INVALID`, `RESPONSE_EVIDENCE_STALE`, `RESPONSE_EVIDENCE_UNSUPPORTED`.

It is called **inside the store's own mutation** at every exit in design section 8:

| Exit | Rule |
| --- | --- |
| `recordCandidateAudit`, `recordSupervisorAudit` | governed: a PASS needs a valid review (structure, binding, derived findings); a FAIL is always preserved |
| `commitPrivateRuntimeAudit` | the same, plus the auditor inclusion receipt in the sealed audit invocation; a governed PASS whose dependencies are stale is recorded as a FAIL with a derived `RESPONSE_EVIDENCE_STALE` finding, so the existing repair loop (which refreshes the snapshot, section 7) or the fallback takes over |
| `approveCandidateForDelivery` | the full check |
| `approveSupervisorDraft` | the full check except dependency freshness: a supervisor approval releases nothing, and export (below) checks freshness with the existing stale outcome |
| `deliverCandidateResponse`, `deliverPrivateRuntimeCandidate` | the full check, atomically with the transcript append |
| `exportSupervisorArtifact` | the full check, from `assessSupervisorArtifact` (the point its comment reserves) |
| `markCandidateSent` | refuses governed candidates, and every candidate under `enforced` (`RESPONSE_EVIDENCE_LEGACY_EXIT_REFUSED`) |
| `savePrivateRuntimeDiscriminator`, `deliverPrivateRuntimeDiscriminator` | section 8 |

Controller and service pre-checks are allowed for better errors but are never the only check.

## 7. Retrieval, budgets and snapshot revisions (slice 2)

- The controller freezes the snapshot at `RECEIVED`, before the first writer invocation, and reuses it after a restart (a completed
  writer is never re-frozen; the existing restart test pattern applies).
- The journal provider call is bounded by `journalTimeoutMs` (default 4,000 ms). A missing provider gives
  `availability: "not_configured"`; a refusal `not_authorized`; an error or timeout `retrieval_status: "failed"`. None of these
  fails the turn: current-message support proceeds without historical claims (design section 9).
- Budgets: at most 8,000 requested journal tokens and 64,000 serialized UTF-8 bytes of journal excerpts per turn, counted on the
  actual excerpts (tokens conservatively as bytes / 3). An item that does not fit is omitted whole with an omission entry; a
  quotation is never cut. Enforced before any model call.
- One batched targeted retrieval before writing; at most one evidence expansion per runtime turn, only when an audit returns
  `missing_material_history` and a provider is configured, inside the same per-turn budget. Cache by case, purpose, generation,
  visibility epoch and query (the existing `createJournalResultCache`).
- Revisions: at `RECONSTRUCTING` the controller creates revision n+1 when the current binding differs from the snapshot's
  (`dependency_refresh`) or for the one expansion (`evidence_expansion`); at most 3 revisions per runtime turn. A revision never
  resets the two-repair limit.
- The session-use adapter, `createSessionUseJournalEvidenceProvider` (behind the existing `freezeForTurn` seam), uses the access
  service's `session_use` purpose checks and `openPrivateJournalGraph({ purpose: "session_use" })`, returns exact excerpts with
  locators and a receipt per call, and is **not wired into any server** in this branch: the production provider stays off until
  its source consent and release criteria are met (plan slice 2).

## 8. Fallbacks and recovery (slice 4)

- At `DISCRIMINATING_QUESTION_REQUIRED` on a governed turn, the stored question is reviewed before it is saved: one model call
  (stage `discriminator_review`, the same packet-only auditor, the same evidence contract on the exact question bytes). The result
  is stored as an additive runtime-turn field `discriminator_review` (bound to the question's sha, the snapshot and the auditor
  context, with the sealed invocation), so the immutable `discriminator` object stays byte-identical to what older builds write.
- Passes: the question is saved and delivered. Fails: the fixed owner fallback is used where it already applies (setting on and an
  allowed route; fixed bytes and policy, so it is the design's "already-authorized history-free fallback" and needs no review);
  otherwise nothing is delivered and the run ends with `PRIVATE_DISCRIMINATOR_EVIDENCE_BLOCKED` (a truthful operational status).
  There is no further repair cycle.
- `deliverPrivateRuntimeDiscriminator` on a governed turn requires either the owner fallback kind or a passing
  `discriminator_review` for the exact bytes with current dependencies.
- No new runtime state or transition (older builds validate the transition ledger on read, so a new one would make cases
  unreadable after a rollback). A candidate found stale at delivery is refused with `RESPONSE_EVIDENCE_STALE` and the turn stays
  `APPROVED`; this is the same class as the existing protective-compatibility refusal and is recorded as a known limit.
- Current-message safety handling never waits on journal retrieval (section 7). With inference or review unavailable the existing
  `THERAPY_RUNTIME_UNAVAILABLE` stands; no offline clinical text is added.

## 9. Supervisor path under enforcement

- `submitSupervisorDraft` freezes (or the service freezes just before a backend writer runs) a snapshot owned by the draft's
  operation key, with the owner's recorded inputs as `relayed_client_message` / `supervisor_instruction` items carrying their
  `supplied_by`. The audit and repair receive the view; `recordSupervisorAudit` validates as in section 6; the service's
  `admissionCheck` hook is wired to the shared check; approval and export run it in the store.
- `review_scope` reports `source_support_coverage: "enforced"` and `owner_inputs_in_audit_packet: true` for governed drafts, and
  the current values otherwise.
- A governed draft whose dependencies went stale before approval keeps the existing supervisor semantics: the review may end `approved`
  (approval releases nothing), the draft is not exportable, and the result carries the existing "the case has changed since" notice;
  export refuses it as `SUPERVISOR_ARTIFACT_STALE`. Never an unhandled error. (Amended 23 Nov 2026 to state the rule built in part B;
  the earlier wording said nothing would be approved.)
- Nothing about the connector's tool list, scopes or the read-only tools changes.

## 10. Behavioral evaluation (slice 6)

`tasks/response-evidence-eval-20261123/`, modelled on `tasks/longitudinal-risk-eval-20261101/` (sealed packets, receipts outside
Git, caps, `INNER_SIGNAL_EVAL_ALLOW_SUBSCRIPTION_CLI=1`, `--live`, the sealed `ClaudeCliProvider`, no API mode, no retries).
Synthetic paired cases with frozen expectations (a planted error and its matched valid control, with French variants); two arms
holding case sources and candidate text constant: **G**, today's generic audit (packet and prompt exactly as `main` builds them),
and **E**, the evidence-aware audit. Scored per case and arm: false approvals, unnecessary blocks, malformed reviews, latency and
tokens; never a pooled reliability rate. A deterministic test runs seal, the mock audit and the scorer (propagation, not
detection). The corpus and its expectations are committed before any live call, and the report names that commit.

## 11. Tests at the consumer seam

Every acceptance case of design section 12 that this branch can reach is a test that calls the real store methods on synthetic
encrypted stores (and the real controller, model runtime packet builders and supervisor service where the case involves them),
including: empty generic PASS without coverage refused; forged, foreign or altered snapshot refused; unrelated genuine quotation
does not certify support (a scripted auditor marking it supported for a dimension its kind cannot support is downgraded); stale
after a correction between audit and commit refused; the real snapshot → first commit → audit → delivery path stays current; restart
reuses the frozen input; the wrapper bypassed and a store exit called directly is still checked; a fallback question with an
unsupported premise is blocked and a neutral one passes; the journal unavailable still lets a current-message reply through; a
competing process is held off by the existing root lock for the new store method; and, with the setting off, behaviour and
packets are byte-identical to `main`.

## 12. Out of scope here (left for later, each with its owner)

Wiring a production journal provider (source consent and release criteria); turning the setting on in production (owner's
release decision); a runtime-turn abandon path for a candidate found stale at delivery (needs a new transition and a rollback
plan); host-side enforcement of free-form chat (design section 10: not claimable); external sending and its outbox.
